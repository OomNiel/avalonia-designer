## 1. Build & run

```bash
npm install                       # ws, @xmldom/xmldom, typescript
npm run compile                   # tsc → out/
dotnet build host/PreviewerHost.csproj -c Debug   # → host/bin/Debug/net8.0/PreviewerHost
```

- Press **F5** (`.vscode/launch.json` → preLaunchTask `build: all` = host + npm compile) to launch an Extension Development Host.
- The extension **auto-builds the host on first designer open** if `host/bin/Debug/net8.0/PreviewerHost` is missing.
- The host is a **persistent child process**; the extension picks a free port and spawns `PreviewerHost --port <port>`; it is killed on `deactivate()`.
- This folder must be opened as its **own workspace** (it is a sibling of `DesignerCS`, outside the old `DesignerCS` workspace root).

- `vsce package --out avalonia-designer-0.1.0.vsix` — answers `y` to the missing

## 3. Architecture & data flow

```
Toolbox (TreeView) ──click-to-arm / click-canvas-to-place──▶ Webview canvas (custom editor for *.axaml)
        (drag-drop also supported; on Linux/Xorg the click-to-place path is the reliable one)
        webview ──postMessage──▶ extension host (TS)
        extension ──WebSocket JSON──▶ PreviewerHost (C#, headless Avalonia)
        host replies: PNG base64 + bounds[{name,type,x,y,width,height}] of every control
```

**Host WS messages (JSON, camelCase replies, `id` echoed):**
- `hello` → `helloAck`
- `ping` → `pong`
- `snippet {tag}` → `snippetResult {tag,name,xaml}` (host generates unique `TagN` name)
- `render {xaml,width,height}` → `frame {png,width,height,controls[],error?}`

**Webview ↔ extension messages:**
- ext→webview: `frame`, `properties`, `status`, `selectControl {name}`, `toolboxAdd {tag}`
- webview→ext: `ready`, `select {name}` (null = root), `deselect`, `setProperty`, `drop {tag,parentName,x,y}`, `move`, `resize`, `delete {name}`, `openEvent {name}`, `openNewForm`
- ext→webview: `armTool {tag}` — clicking a toolbox item arms the tool (crosshair cursor + status
  prompt); the next canvas click places the control at that point (`drop`). Esc cancels.
- **Maiden-form hint:** dropping the first control auto-removes the template's
  "Drop controls here from the Toolbox" TextBlock (`XamlModel.removeDropHint()`).
- **Centred overlay removed:** the old `#dropHint` ("Drop a control here") centred overlay was
  removed entirely (2026-08-22) — it proved unreliable/annoying. Only the top-left maiden-form
  TextBlock remains, removed on first drop via `XamlModel.removeDropHint()`.- **Auto-wire on placement:** dropping an interactive control immediately wires its default
  event + inserts the code-behind stub (Button→`Click`, CheckBox/RadioButton→`IsCheckedChanged`,
  TextBox→`TextChanged`, ComboBox/ListBox/TabControl/DataGrid→`SelectionChanged`). Layout
  containers / non-interactive types are NOT auto-wired (`hasDefaultEvent()` in codeBehind.ts).- **Double-click a control** → `openEvent {name}` → wires the control's default event into
  the XAML (`Click="Button1_Click"`, `TextChanged`, `IsCheckedChanged`, `SelectionChanged`,
  fallback `DoubleTapped`), saves it, then opens the code-behind (`.axaml.cs`/`.axaml.vb`,
  created if missing) with the handler stub inserted and the cursor placed in the body.
  Re-double-clicking is idempotent (re-opens at the existing handler).
  **Auto-names are promoted:** if the control only has an in-memory auto name (`_TagN`), it is
  promoted to a clean persisted name (`_Button1` → `Button1`, via `XamlModel.setExplicitName()`)
  before wiring the handler, and the canvas re-renders. Only a truly nameless control warns and
  does nothing.
**Designer is OPT-IN (not the default .axaml editor).** Opening an `.axaml` shows the
normal text editor; the designer opens via Explorer right-click → **Avalonia: Open in
Designer** (`avaloniaDesigner.openInDesigner` → `vscode.openWith` the custom editor
viewType). `customEditors.priority` is `"option"` (was `"default"`), and the command is
hidden from the command palette (needs a resource arg).

## 4. Key technical decisions & gotchas (IMPORTANT)

1. **No public string XAML loader in Avalonia 11.0.10.** `AvaloniaXamlLoader` only has
   `Load(object)`, `Load(Uri,Uri)`, `Load(IServiceProvider,...)`. So XamlRenderer uses
   three strategies in order:
   1. Internal `IRuntimeXamlLoader` **via reflection** (`AvaloniaXamlLoader+IRuntimeXamlLoader`,
      `RuntimeXamlLoaderDocument(xaml)`, `RuntimeXamlLoaderConfiguration`, `AvaloniaLocator.Current`
      → `GetService`). Full-fidelity.
   2. Temp-file + `AvaloniaXamlLoader.Load(uri, uri)`.
   3. Programmatic builder from the XML (common designer format only).
   Pattern ported from the VB host `/home/niel/Projekte/Avalonia/DevHelper/DesignerHost/`.

2. **Namespaces:** `UseHeadless` + `AvaloniaHeadlessPlatformOptions` live in namespace
   **`Avalonia.Headless`** (you must `using Avalonia.Headless;`). `UseSkia()` comes from the
   `Avalonia.Skia` package.

3. **Do NOT use `CaptureRenderedFrame`.** Render synchronously with
   `new RenderTargetBitmap(new PixelSize(w,h), new Vector(96,96))` then `rtb.Render(window)`.
   Works without any dispatcher pump.

4. **Headless window is stuck at 1024×768.** The public `ClientSize` setter is internal, so the
   host forces it via reflection:
   `typeof(TopLevel).GetProperty("ClientSize", Public|NonPublic).SetValue(window, new Size(w,h))`.
   Without this the design surface would be the wrong size.

5. **Control identity is by NAME, not index.** The host's logical-tree DFS (`ILogical.LogicalChildren`)
   includes internal nodes (`AccessText`, `ContentPresenter`, …) that are absent from the XAML DOM,
   which breaks index-based matching. Fix: `XamlModel.ensureNames()` auto-assigns an in-memory
   `x:Name` (`_TagN`) to every non-root control before rendering; `serialize(forSave=true)` strips
   them again so saved files stay clean. All mapping (select/move/resize/properties/drop-parent) is
   by name; `name:null` = the root element.

6. **`DataGrid` type is in namespace `Avalonia.Controls`**, not `Avalonia.Controls.DataGrid`
   (the assembly is `Avalonia.Controls.DataGrid`, namespace is `Avalonia.Controls`).

7. **TypeScript config:** `@xmldom/xmldom` types come from `lib.dom`, so `tsconfig` **must**
   include `"DOM"` in `lib`. `@types/vscode` (1.134) requires `saveCustomDocumentAs()` on a
   `CustomEditorProvider`. Use `module: "node16"` + `moduleResolution: "node16"` (package.json has
   no `"type":"module"`, so it still emits CommonJS).

8. **Move/resize semantics:** on a `Canvas` parent, move sets `Canvas.Left`/`Canvas.Top` (absolute).
   Elsewhere it adjusts `Margin` (best-effort). Resize always sets `Width`/`Height`.

9. **Avalonia 11 has NO `Visibility` enum property — use `IsVisible` (bool).** The old generic
   Properties list exposed `Visibility` (Visible/Hidden/Collapsed), which would have broken
   the previewer render if set. The catalog uses `IsVisible`.

11. **Event handlers must be stripped from the PREVIEW XAML.** The headless host cannot
    resolve code-behind handlers, so `Click="..."` etc. would break the render. `XamlModel`
    keeps an `EVENT_ATTRS` set and `serialize(forSave=false)` (the render pass) strips them;
    `serialize(forSave=true)` (save/undo) keeps them. The event attribute is written to disk
    but never shown on the canvas — so after dbl-click the canvas is NOT re-rendered.

12. **Code-behind discovery must match BOTH naming conventions.** The dbl-click handler looks
    for the code-behind as `<Name>.axaml.cs/.vb` (VS/Avalonia default) AND `<Name>.cs/.vb`
    (alternative — e.g. DevHelper uses `AboutWindow.vb`). It prefers the file that already
    declares the form's class (avoids creating a duplicate partial class), else the first
    existing candidate, else creates one. Generated VB code-behind needs
    `Imports Avalonia.Controls` or `Inherits Window` fails (BC30002).
    (Bug hit 2026-08-22: DevHelper got a bogus `AboutWindow.axaml.vb` duplicate → fixed by
    preferring `AboutWindow.vb` and deleting the duplicate.)

13. **VB code-behind requirements (New Form template).** For VB projects (DevHelper) the New
    Form code-behind must:
    - `Imports Avalonia.Controls` (else `Inherits Window` → BC30002 "Window is not defined"),
    - define `InitializeComponent` manually via `AvaloniaXamlLoader.Load(Me)` (VB does NOT
      auto-generate it → else BC30451), so `Imports Avalonia.Markup.Xaml` is also needed,
    - and the XAML `x:Class` must be fully qualified (`DevHelper.frmTest`), because VB applies
      the project root namespace to global-namespace classes → else Avalonia AVLN2000
      "Unable to find type". `buildAxaml` now uses `${rootNamespace}.${name}` for both languages.
    Same rules apply to `codeBehind.ts`'s `createCodeBehind` fallback template.

10. **Property catalog is verified against the real assemblies.** `src/propertyCatalog.ts`
    was built from a reflection dump of the public instance properties of each control type
    in the host's `Avalonia.Controls.dll`/`Avalonia.Controls.DataGrid.dll` (Avalonia 11.0.10,
    via a throwaway reflection tool). Key findings: **font props (`FontFamily`/`FontSize`/
    `FontWeight`/`FontStyle`/`Foreground`) exist ONLY on text-capable (TemplatedControl) types**
    — panels, `Border` and `Image` have none; `CornerRadius`/`Padding`/`BorderBrush` are also
    TemplatedControl-only (TextBlock has `Padding`+`Background` but no CornerRadius); `Panel`/
    `Grid`/`Canvas` have `Background`; `Image` has none.
    Custom **Window-derived roots** (e.g. `chrome:ChromeWindow`) resolve to the `Window`
    property set (Title, CanResize, WindowStartupLocation, SystemDecorations, Icon, ...) plus
    ChromeWindow-specific `TitleBarTitle`/`TitleBarIcon` (`isWindowLike` = tag is `Window` or
    ends with `Window`).

### Bug fix (2026-08-23): placing any control crashed on ChromeWindow-rooted forms
The "Avalonia VB Projects" generator (`create-avalonia-vb`) produces a form whose root is
`<chrome:ChromeWindow>` and — crucially — declares the `MainWindow` class **inside `Program.vb`**
(there is NO `MainWindow.vb` / `MainWindow.axaml.vb`). Three bugs this exposed:
1. **`Cannot read properties of undefined (reading 'indexOf')` on every drop.** `resolveDropTarget`
   walked UP from the root looking for a container; a custom root (`ChromeWindow`) is NOT in
   `CONTAINER_TAGS`, so it reached the XML **Document** node whose `tagName` is undefined →
   `localName(tagName)` crashed. Fix: treat window-derived roots like Window
   (`ln === 'Window' || /window$/i.test(ln)`), skip property elements when descending into single
   content (`.Resources` etc.), and guard `cur.nodeType !== 1` before reading `tagName`.
2. **Wrong base class in a freshly-created code-behind.** `createCodeBehind` detected the root via
   `/<([A-Za-z][\w.]*)/` which stopped at the `:` (matched only "chrome"), so it generated
   `Inherits Window` for a `ChromeWindow` root. Fix: capture prefix + local name, resolve
   `xmlns:chrome="using:AvaloniaChrome"` → base class `AvaloniaChrome.ChromeWindow` (fully-qualified).
3. **Duplicate class / BC30179 when creating a code-behind for the generator's MainWindow.**
   `insertHandlerIntoCodeBehind` only checked `<Name>.axaml.cs|vb` / `<Name>.cs|vb`, none existed →
   it created a NEW `MainWindow.axaml.vb` while `Program.vb` already declared `MainWindow` → build
   conflict. Fix: scan sibling `.cs/.vb` files for a file declaring `Class MainWindow` and insert
   there; also insert into the class matching the form name (Program.vb contains `App`, `MainWindow`
   AND a Module — don't target the first `Class`).
**Verified:** sandbox copy of TestVBApp → handler lands in `Program.vb` inside the `MainWindow`
class → `dotnet build` 0 warnings / 0 errors. DevHelper `AboutWindow` regression check still OK.

### Bug fix (2026-08-23): controls "disappear" when moved into a new/nested Canvas
**Reported:** moving a control to "➕ New Canvas…" deleted it from the old container and it vanished.
**Root cause (proven by driving the real host + standalone probes):**
- The PreviewerHost's full-XAML load (IRuntimeXamlLoader reflection → temp-file → programmatic
  fallback) **never succeeds on Avalonia 11.0.10**: the `IRuntimeXamlLoader` service is not
  registered even with `Avalonia.Markup.Xaml.Loader` referenced/force-loaded (probe returned null;
  `AvaloniaXamlLoader.Load` throws "No precompiled XAML found").
- So the host ALWAYS uses the programmatic fallback, which built **only the top panel's DIRECT
  children**. A control nested 2+ levels (e.g. `StackPanel > Canvas > Button`) was never created →
  invisible, and the Canvas collapsed to `h=0`.
**Fixes:**
1. `host/XamlRenderer.cs` — `CreateControlFromElement` now **recurses into children** for
   `Panel`-typed controls, so nested containers render (verified: `StackPanel > Canvas > Button`
   now reports the button in plain and ChromeWindow-rooted forms).
2. `src/designerPanel.ts` — New Canvas now creates `<Canvas x:Name="…" Width="240" Height="140"/>`
   so the free-placement area is visible instead of an empty strip.
3. `src/hostClient.ts` — auto-build now **rebuilds when any host source file is newer than the
   binary** (`hostSourceIsNewer`); previously it only built if the binary was missing, so installed
   copies could keep a stale host with old bugs.
**Note:** "New Canvas" still places the Canvas *inside* the current container (e.g. inside the
StackPanel) — the control is free within the Canvas, but the Canvas occupies a stack slot. Moving a
control truly outside the StackPanel requires a different root layout (e.g. a Canvas-rooted form).

### Dock property (2026-08-23) — dockable controls

- `PropTemplate` gained `emptyValue`; `propertyDefsFor` shows `Fill` when unset. GOTCHA: xmldom's
  `getAttribute` returns `''` (not null) for missing attrs → use `||` not `??` for the emptyValue
  fallback (fixed 2026-08-23).
- Host (`XamlRenderer.ApplyProperty`) now applies `DockPanel.Dock` via `DockPanel.SetDock`, so the
  preview actually docks (verified: Menu docks top, StatusBar docks bottom, content fills).
- **StatusBar Dock fix:** the Status Bar tool inserts a **Border** (no StatusBar control exists), so
  selecting it showed only Border props and Dock was missing. `propertyDefsFor` now detects
  StatusBar-named elements (`/^StatusBar\d*$/`, same trick as `infoTagFor`) and merges the
  StatusBar props (Dock, Background) with the Border styling props (Background/BorderBrush/
  BorderThickness/CornerRadius/Padding).
- **Fill semantics (user-specified):** Dock Left/Right stretches vertically & aligns to the side;
  Dock Top/Bottom stretches horizontally & aligns to the edge; Fill fills remaining space without
  covering others; docked controls sit adjacent when a side is occupied. All native to Avalonia's
  DockPanel EXCEPT Fill only fills for the LAST child (`LastChildFill`). So the designer now, when
  Dock=Fill is set on a control whose parent is a DockPanel, **removes the Dock attr AND moves the
  control to be the last child** (`parent.appendChild(el)`) so Fill works regardless of position.
  Only one control can fill (the last one).
- **"Docking does nothing" bug (2026-08-23, found by automated test on TestVBApp/frmTest):**
  The docked control was the ONLY child of a DockPanel → it's the **last child** → `LastChildFill`
  (default True) makes it FILL regardless of its Dock → changing Dock had zero visible effect
  (render bounds identical for every value). ALSO, controls had leftover explicit `Width`/`Height`
  and big drag `Margin` which prevented the dock stretch. Fixed in `setProperty`:
  - on ANY dock (side or Fill): clear `Margin`, `Canvas.Left/Top`, and the explicit size on the
    FREE axis (Height for Left/Right, Width for Top/Bottom, both for Fill);
  - side-dock on the LAST child → set parent `LastChildFill="False"` so the dock applies;
  - Fill → move to last + `LastChildFill="True"`.
  Verified on frmTest: Left=(48,22 260x378), Top=(48,22 697x24), Right=(485,22 260x378),
  Bottom=(48,376 697x24), Fill=(48,22 697x378). Also cleaned the real frmTest.axaml (removed stale
  Height/Margin, added LastChildFill=False); TestVBApp still builds 0/0.
- **Dock-switch vanish bug (2026-08-23):** changing Left->Bottom made the control disappear — the
  Left dock had removed `Height` (free axis) and Bottom then removed `Width`, so the control had no
  size at all and collapsed to 1px. Fix: on side-dock, keep/ensure the THICKNESS axis (Width for
  Left/Right, default 200; Height for Top/Bottom, default 24). Verified Left->Bottom renders
  (48,376 697x24) — visible.
- **Default docks (2026-08-23):** Menu tool snippet now ships `DockPanel.Dock="Top" Height="24"`

- **Root Canvas fill:** at runtime a Window stretches its content (so a root Canvas fills), but the

### VB event-handler args (FIXED 2026-08-25): auto-wired handlers now use the exact EventArgs type
- Previously, auto-wired VB handlers always used
  `Private Sub Xxx(sender As Object, e As Avalonia.Interactivity.RoutedEventArgs)`. Avalonia's
  XAML compiler requires the signature to match the event delegate exactly (VB is strict; C#
  tolerates it via contravariance), so `DoubleTapped`, `SelectionChanged` and `TextChanged`
  handlers failed to build with `AVLN:0004`.
- FIX: `src/codeBehind.ts` — `vbEventArgsFor(eventName)` maps the event to the exact VB args
  type (`Tapped`/`DoubleTapped`/`RightTapped`/`Holding` → `Avalonia.Input.TappedEventArgs`,
  `SelectionChanged` → `Avalonia.Controls.SelectionChangedEventArgs`, `TextChanged` →
  `Avalonia.Controls.TextChangedEventArgs`, everything else → `RoutedEventArgs`). The event name
  is now passed through `insertHandlerIntoCodeBehind` → `insertVbMethod`. Applies to NEWLY
  generated handlers; pre-existing broken ones in a user's code-behind must be fixed manually.

### VB named-control accessors (2026-08-25): `TextBox2.Text = ...` just works
- In VB, named controls are NOT auto-generated fields (unlike C# where a partial class gets a
  field per x:Name), so referencing `TextBox2` in a handler failed with BC30451. FIX: the
  designer now keeps a set of **read-only accessor properties** in the VB code-behind, one per
  named control:

      Get

      End Get
  End Property

## 7. Known limitations (v1)

- Moving is only truly absolute inside a `Canvas`; elsewhere it uses `Margin` ("when applicable").
- Custom/third-party controls the host can't load render as approximations or an error card
  (full support would require compiling user assemblies into the host).

  re-formatted on save (comments kept, whitespace normalised).

  to place it at that position (`armTool` → `drop`).
- New-form template defaults the root layout to `Canvas` (so move works absolutely). Could be
  switched to `Grid` if preferred.

## 18. Robust double-click (single-click never opens the code-behind) (2026-08-25)

Bug: **occasionally a single left-click on a placed control lost designer focus and jumped to the
code-behind editor** (e.g. `MainWindow.axaml.vb`).

Root cause: `media/designer.js` used the browser's **native `dblclick`** on the canvas to open the
code-behind. The per-control overlays (`.ov`) are `pointer-events: none`, so EVERY click (on any
control or the empty canvas) targets the **canvas** element. So any two clicks within the OS
double-click interval — even on **different** controls, or a "select, then select again" — fired
the canvas `dblclick`, which hit-tested the second click and opened the code-behind. Single-click
selection posts `{type:'select'}` (that handler never opens an editor); the only editor-opening
path was `openEvent` → `openEventHandler` → `wireDefaultHandler(openEditor=true)` →
`showTextDocument`.

Fix (`media/designer.js` only): **removed the native `dblclick` listener** and detect a deliberate
double-click inside the `click` handler. A double-click now requires the two clicks to be:
- within **500 ms** of each other,
- within **10 px** of each other,
- on the **same control** (same hit-test name).

Otherwise the second click is just a normal single click (select). Toolbox place-mode clicks
(`state.pendingTag`) are handled *before* the double-click check, so place mode never opens the
code-behind. Clicking the selection rectangle still records the click, so double-clicking an
already-selected control keeps working. Verified with `node --check`; packaged + installed.

## 20. TabControl body controls appeared TWICE in the control drop-down (2026-08-26)

`TabControl2Body1Canvas` Canvas) twice in the Properties control drop-down.

selected tab's content is reachable through TWO logical parents — once as the `TabItem`'s

walked the logical tree and therefore visited the same DockPanel/Canvas twice, reporting

template-internal controls are still all reported (they are distinct, e.g. the three TextBlocks:
title bar, status text, tab header). Reproduced + verified with `/tmp/tabdup.js` (before: 15
